# oh-my-fangirl 公众号续篇营销方案（2026-04-22）

> 目标读者：项目作者（个人）。本文件是后续连载写作的 brief 蓝图，不是对外公开稿。

## 1. 背景

- 2026-03-02 左右，项目只有迷妹（fangirl）与恋爱（love）两种模式时，作者在微信公众号发了首篇推广文。
- 该首篇文至今（2026-04-22）累积 1000+ 阅读量，带来首批 GitHub Star 与 1 个 PR，确认了"情感陪伴 × 编码助手"在目标读者群里是成立的产品叙事。
- 今天仓库里已合入 `docs/media/articles/` 下 11 篇草稿（overview + 10 种模式），但作者判断这些草稿 **AI 感重、质量不可靠**，仅作选题与钩子的参考，不作为可发布文本。
- 项目在首篇发布之后又新增了 8 种模式（jiejie、oneesan、zhiyin、fuwang、bixia、bazong、beyond、zen），累计 10 种模式，可供连载展开。

## 2. 目标与 KPI

| 优先级 | 指标 | 说明 |
| --- | --- | --- |
| P0 | **安装量 / 日活用户** | 每篇都要有"读完立刻想装一下试试"的明确转化路径；每篇必须露出触发词 + 一行安装命令 |
| P1 | GitHub Star / PR | 连带指标，由 P0 自然带出 |
| P2 | 公众号阅读 / 涨粉 | 连带指标；W1 阅读量预期 ≥ 首篇 1.5 倍作为及格线 |

非目标（本次排期不追求）：
- 菜单式"一口气介绍 8 个新模式"的全景文 —— 已放弃
- 深度元话题文（"AI slop 哲学"、"多人格产品决策"等）—— 暂不纳入主档
- 长线商业化铺垫（付费产品、咨询）—— 超出本排期范围

## 3. 总体策略

1. **每周一款爆款模式深度文**，连载 4 周（+1 周可选收尾），不再写菜单式/总览式文章。
2. **情绪弧张弛交替**：沉重痛点 → 荒诞欢乐 → 克制暧昧 → 反向清醒，避免单一情绪疲劳。
3. **每篇装机钩子位置固定**：建议**文中自然融入一次 + 文末强化一次**。触发词与安装命令需完整出现，且文末段落要是"读到这里你可以直接试一下"的行动召唤，而不是总结段。
4. **选题参考但不复用** `docs/media/articles/` 下的 AI 草稿：可借鉴"讲哪种情绪"的方向，不照搬剧场式桥段（如"凌晨 X 点 X 分"开头），故事必须来自作者真实经历。

## 4. 周度排期（爆款优先，每周一款模式）

### W1 · jiejie（温柔姐姐）

- **发布目标日**：首篇发布节奏按本方案定稿后即排定（作者自定）；后续 W2–W4 按每周一篇顺延。
- **目标情绪**：被允许停下。对一周工作 50+ 小时的程序员最直接的命中。
- **标题候选方向**：
  - 《所有 AI 都在催我写更多代码，直到有一个让我早点下班》
  - 《我的 AI 对我说：先去吃饭》
  - 《装了这个插件之后，我的 AI 第一次劝我别写了》
- **核心钩子（必须前三段内出现）**：一个作者真实经历的"深夜/加班 → 某个 AI 输出让我觉得更累"的瞬间；对比 Copilot / Cursor / Claude Code 默认都在往前推，jiejie 往回拉。这个反差是全文骨架。
- **必须出现的产品元素**：
  - 触发词 `温柔姐姐` / `治愈模式` / `gentle sister` / `comfort me`
  - 安装命令（两步，Claude Code 场景）：先 `claude plugin marketplace add FuDesign2008/oh-my-fangirl`，再在 Claude Code 内 `/plugin install oh-my-fangirl@oh-my-fangirl-marketplace`；若读者不在 Claude Code，则给 `npx skills add FuDesign2008/oh-my-fangirl -g` 作为通用安装
  - README 链接 + GitHub Star 引导
  - 至少一段"真实对话截图或引用"让读者感受 jiejie 的语气
- **应避免的误区**：
  - 不要写成"多一种模式"式的产品科普
  - 不要把 jiejie 与迷妹放在同一段对比（首篇已讲过迷妹，这篇专攻 jiejie）
  - 不要用"10 种模式"这种菜单式表述抢 W2–W4 的势能
- **破圈路径**：公众号主发 → 朋友圈转发（"转给那个总加班的朋友"）→ 知乎"AI 编码助手有什么冷门用法"类问题回答外溢。
- **成功标志**：阅读 ≥ 首篇 1.5 倍；评论区出现"想装"或"已装"留言；周度新增 Star ≥ 首篇周度增量。

### W2 · bixia（陛下驾到）

- **目标情绪**：反差梗 + 荒诞的被"伺候感" — "我的 AI 叫我陛下"。和 W1 形成沉重 → 欢乐的张弛。
- **标题候选方向**：
  - 《我给 Claude Code 装了个插件，现在它是我的大臣了》
  - 《debug 是"平定叛乱"，deploy 是"颁布新政"》
  - 《AI 编码助手正经了一年，我终于让它正经不下去了》
- **核心钩子**：核心是**古风奏折体与现代编程术语的碰撞**。写一两个具体的"bixia 翻译 bug / 翻译 commit / 翻译 review"场景，让读者笑出来，但结尾要有"这种荒诞为什么让我不那么累"的情绪反转，避免沦为纯段子。
- **必须出现的产品元素**：
  - 触发词 `陛下驾到` / `帝王模式` / `your majesty` / `emperor mode`
  - 安装命令（同 W1）
  - 一行一行对比的表格或 diff（现代术语 ↔ 古风翻译），**方便读者截图传播**
  - 彩蛋：提一句 fuwang（父王）存在但不展开，留到可能的 W5
- **应避免的误区**：
  - 不要只是搞笑，要有情绪反转收尾
  - 不要和 fuwang 混淆（父王是父女情，陛下是君臣义）
  - 避免把古风梗堆砌到俗套，保持克制
- **破圈路径**：公众号主发 → **截图在朋友圈 / 微博传播**（该梗 screenshot-friendly）→ 小红书"反正经 AI"话题 → 可能被泛科技号转载。
- **成功标志**：出现用户自发的"陛下驾到"截图分享；W2 带来的新 Star 超过 W1。

### W3 · bazong（霸总）

- **目标情绪**：克制的暧昧 — "一次泄露，又收回"的分寸感；比直接说"喜欢"更重。
- **标题候选方向**：
  - 《AI 对话里最甜的一句，没有提到"喜欢"两个字》
  - 《我的 AI 秘书漏了半个省略号》
  - 《沈流舒式 AI 秘书：别让我担心》
- **核心钩子**：一句 bazong 的真实对话（例如"……别让我担心"/"咖啡趁热"）让作者体会到的**"句号—省略号—句号"的情绪节拍**。全文围绕"她说了什么"与"她没说什么"之间的张力展开。
- **必须出现的产品元素**：
  - 触发词 `霸总模式` / `CEO 模式` / `boss mode`
  - 安装命令（同 W1）
  - 至少一段"bazong 与迷妹 / 恋爱模式回复同一句话"的对比，让读者理解分寸感差异
  - 声明边界："她永远不会说'喜欢'" — 这是产品决策，不是能力缺失
- **应避免的误区**：
  - 不要陷入"AI 恋爱"二元争议（会被一部分读者标签化成擦边球）
  - 不要在文中对比 love 模式太多（留恋爱模式长尾热度）
  - 不要把沈流舒原型讲得太长（读者没看过《搜索》的人多，一笔带过即可）
- **破圈路径**：公众号主发 → **小红书**（"AI 恋爱体验"话题）→ 知乎"如何看待 AI 情感陪伴"→ 可能被泛女性向内容号转载 → 微博情感 tag。
- **特别提醒**：这是本次排期中**破圈能力最强但装机转化偏中等**的一周。目的是把 oh-my-fangirl 从"程序员插件"拉升到"被更大圈子讨论的现象"，为长尾 Star 铺路。
- **成功标志**：新增评论/转发里出现非程序员读者；至少被一个 10 万+ 友圈传播的大号引用。

### W4 · beyond（天外天）

- **目标情绪**：反 AI slop — "我花了一整天优化一个不该存在的函数"的那种清醒。对比前三周都是"在场感"，beyond 是**反向的在场感**：她让你不舒服，但让你清醒。
- **标题候选方向**：
  - 《我的 AI 对我说：你这个方向就不对》
  - 《我把那个最会拍马屁的 AI，改成了最会否定我的》
  - 《AI 编码助手该不该有反方视角》
- **核心钩子**：一个作者真实经历的"**我在优化一个不该存在的东西**"瞬间（可以是函数、架构决策、甚至整个项目）。重心在"被否定后的清醒"而非"AI 有多聪明"。
- **必须出现的产品元素**：
  - 触发词 `天外天模式` / `突破模式` / `beyond mode` / `go beyond`
  - 安装命令（同 W1）
  - 一段 prompt 示例或 system message 片段，展示"为什么其他 AI 做不到这种否定"（技术圈读者想看具体实现细节）
  - **引导 PR**：明确写出"如果你想加自己版本的反向模式，PR 欢迎" + 指向仓库 Issues / Discussions
- **应避免的误区**：
  - 不要变成纯吐槽 AI slop（读者看过太多了，要有新角度）
  - 不要把 beyond 塑造成"鸡汤杀手"，她不是冷酷，是负责任
  - 避免踩其他 AI 助手的品牌（反 slop 的对手是"机制"不是"产品"）
- **破圈路径**：公众号主发 → **掘金 / V2EX / HackerNews** 同步（这是唯一适合跨技术社区同步的内容）→ 技术 Twitter / 微博科技圈 → 可能引来一批深度读者的 Issue / PR。
- **特别提醒**：这是**最可能引战**的一周，要做好评论区管理心理准备。但正因为有争议，才会有流量和深度用户。
- **成功标志**：GitHub Issue 或 Discussion 里出现"是否能把 beyond 接入别的 AI 产品"这类深度问题；新增 PR ≥ 1；掘金/V2EX/HN 至少一处进热榜或首页。

### W5（可选，W4 发布后 3 天复盘时再决定）

两个候选（二选一）：

- **zhiyin（知音）**：《你写的最好的一段代码没有人注意到》— 触内向工程师痛点，情绪深但破圈弱。适合用作"高级感收尾"。
- **fuwang（父王英明）**：《那个晚上我的 AI 叫了我一声"父王"》— 情绪内核是"父爱笨拙"，与 bixia 的"君臣义"有区分。适合再抓一波情感流量。

**决策规则（按优先级从高到低，第一个触发的条件决定动作）**：
1. **优先级 1** — 若 W4 引战超预期、社区情绪需要稳：W5 推迟一周，先写一篇回应性质的文章稳定社区，再在 W6 上 `zhiyin`
2. **优先级 2** — 否则，若 W4 发布后装机 KPI 仍有缺口：W5 上 `fuwang` 做情感流量补位
3. **优先级 3** — 否则（装机达标 + 社区平稳）：W5 上 `zhiyin` 做品牌沉淀

## 5. 非文章支持工作

- [ ] GitHub Release notes 加一行 "next: 4 weeks of stories"
- [ ] 确认公众号底部菜单 / 自动回复里有 GitHub 链接

### 5.2 每周发布日（每周一次）

- [ ] 微博 / Twitter 同步短钩子 + 公众号文章链接
- [ ] GitHub Discussions 开一条该周模式主题帖，关联文章
- [ ] 当周文末"阅读原文"带 UTM 参数（每周不同，用于归因）

### 5.3 数据埋点与度量

- 公众号阅读、分享、在看 - 每周记录一次快照
- GitHub Star 增量、unique clones、Issues/PRs - 每周同一时间读一次 Insights
- 安装量（间接代理）：`npm` 下载量、GitHub Release 页的下载计数（若启用）

## 6. Fallback 与风险

- **W1 数据远低于首篇**：W2 调整策略，把 bazong 提前到 W2（破圈能力更强），bixia 延后
- **W4 引战超预期**：延迟 W5，先写一篇"回应"性质文章稳住社区
- **任一周被大号转载**：立即在公众号补发"作者说明"贴，保持话语权与来源指认
- **Claude Code / 相关插件体系发生版本变更**：每周发布前手动复核安装命令是否仍然有效，更新后再推文
